The one-page map of piOrchestrator

You already live in parts of this codebase. This lesson connects your islands into one model.

What this is, in one sentence

piOrchestrator is a deterministic, sequential multi-agent workflow engine that runs inside the Pi coding agent. It takes a route and a request, runs a fixed sequence of role sessions, and decides everything itself — which agent runs, what it may touch, when to ask you, and whether the result is acceptable.

Sources: README.md (opening), AGENTS.md §Architecture

The one idea to internalize

The core inversion

The orchestrator owns every transition, validation decision, and retry limit. Agents cannot advance workflow state themselves.

This is the opposite of an "agent swarm" where agents decide what to do next. Here, agents are disposable workers: they receive a task envelope, produce a structured response, and the engine validates it and moves the state machine forward. No role session can ask for more tools, change the plan's scope, or start the next phase on its own.

Source: README.md §Workflow — "The orchestrator owns every transition, validation decision, and retry limit. Agents cannot advance workflow state themselves."

You saw this inversion from the inside when we built the arrow-key feature: the interview's question hub and the parked prompts are engine-owned coroutines, and the agent only ever emits a validated action. Same pattern everywhere else.

The canonical pipeline

Every route shares the same front half, then branches:

Explore→ Plan→ Plan review→ Human gate→ Check setup→ Baseline→ Tester→ Builder→ Review + fixes→ Docs→ Final checks→ Worktree sync
  • Read-only routes (review_only, investigation_only) stop after their route-specific read-only result — never checks, never mutation agents.
  • Planning-only routes (planning_only) complete right after approved planning.
  • Mutation routes continue past the human gate: check setup is deferred until the plan is approved, then a green baseline, then the fixed mutation/review/finalization phases.
Why deferred check setup?

Because read-only routes should be usable on projects with no checks at all. Discovered checks are never executed or saved without your explicit approval — and only mutation routes need them.

Sources: README.md §Workflow, §Workflow routes, §Configuration; AGENTS.md — "Check setup is deferred until a mutation route is approved"

Routes and roles

The user picks one of eight validated routes; the orchestrator then owns the route's fixed phase sequence. Roles come in two capability classes, enforced at four boundaries (config, session, tool-call, post-session diff):

ClassRolesToolsFiles
Read-onlyExplorer, Planner, Reviewer, Debugger, Interviewerread, grep, find, lsInspection targets only
MutationTester, Builder, Documenter+ write, editExact plan files / testSupportFiles

Two details that make this safe: roles run as in-memory Pi SDK sessions with nested extensions, skills, and shell access disabled; and project checks are orchestrator-owned pi.exec calls — an agent can never run your test suite itself.

Sources: README.md §Role tools, §SDK execution; AGENTS.md §Safety And State

Where you live in it

  • Mission Control — the TUI overlay (/orchestrator-control); a read-only window into agent activity. It closes before every human decision point and reopens when the workflow continues.
  • Browser dashboard — optional React console (127.0.0.1, SSE live state) with Overview / Agents / Timeline / Artifacts tabs.
  • /requirements — the interactive interview you've been building: question hub, dashboard-vs-TUI decision race, and handoff into a workflow via startWorkflow.

Practice

Trace it yourself (5 minutes)

  1. Open README.md and read §Workflow and §Workflow routes.
  2. Open src/index.ts — find the /orchestrate handler. It collects the route+request, then calls engine.start(...) and returns immediately.
  3. Open src/orchestrator.ts — the thin facade. start() delegates to runWorkflow in src/orchestration/orchestrator-workflow.ts.
  4. Grep for routePhases or the route table in src/orchestration/orchestrator-routes.ts — that is where the fixed templates live.
  5. Find on your own: which file owns the human gate for plan approval? (Hint: it lives in src/orchestration/ and its name contains "human".) Open it and confirm the gate pauses, doesn't guess.
